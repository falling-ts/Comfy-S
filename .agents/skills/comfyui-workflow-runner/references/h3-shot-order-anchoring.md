# H3 镜头顺序与时长：散文管不住，硬锚定能钉死 —— 但非必要不加（多轮实测）

本机实测（RTX 4060 8GB / H3 `ref2va` + turbo 4 步 LoRA / 832×480 / 15s = 362 帧 /
种子固定）。对象 = `workflows/0044_参考视频.json` 第 1 行 `00001_书房开场四镜`，数据表
`stories/七纹刻印/0044_参考视频.md`。文中每个数字都可用 `scripts/motion-profile.py` 加抽帧复核。

> 术语区分：本文的**硬锚点**指 `MiniMaxH3AddGuide` / `FallingTSH3AddGuide` 的 `frame_idx`（把某张图钉在第 N 帧）。
> 与 `scripts/verify-anchor-snapping.py` 里的「参考视角吸附」是两回事。

> **⚠️ 备注（2026-10-01）：不加硬锚点，效果更好。**
> 硬锚点确实能把镜头顺序／时长钉死（§4 实测），但实际观感不如不加锚点的纯软参考；因此
> `workflows/0044_参考视频.json` 已改回**无锚点的通用版**（参考图直连 `ref_images`，换行只换内容、不用改接线）。
> 硬锚点由「默认做法」降级为**可选手段**：只在顺序／时长必须钉死、散文反复定不住时才上。
> 下文 §4 的接线配方、§4.5 的行号／节点号都是**当时的实现快照**，保留作需要时的参考，不代表 0044 现状。

## 一、问题长什么样

提示词写的是三镜：`[Shot 1]` 0–7s（雨天窗特写 → 一次连续拉镜 → 越肩宽景他在打字）、
`[Shot 2]` 7.0s 切入 `<Picture 5>` 手部特写并连打键盘、`[Shot 3]` 11.0s 切正面。
用户诉求：**第一镜里敲键盘太僵、几乎不动**。

只改散文的后果是：手写活了，镜头顺序却被打乱 —— `<Picture 5>` 的手部特写被搬到视频开头。

## 二、散文四连败（每轮都真跑 + 抽帧）

| 轮次 | 只改提示词的改法 | 手部特写实际落在 |
|---|---|---|
| 改造前 | 动作只写「几下轻敲 + 停顿一拍 + 抬手」 | 7.6–11.2s（位置对，但手基本不动：特写里只有约 1 秒在动、紧接 1 秒完全冻结） |
| 1 | 连 `[Shot 1]` 的敲击一起写活 | **2.4–6.9s**（7 秒连续拉镜被压成 2.5 秒） |
| 2 | `[Shot 1]` 改为「体态级节奏」+ 明令不切特写、镜头不推近 | **3.0–8.2s** |
| 3 | `summary` 里正面写死三镜先后顺序 | **3.0–7.0s** |
| 4 | `[Shot 1]` 逐字还原，只改 `[Shot 2]` | **3.0–8.4s** |

**4/4 都把特写提到了 `[Shot 1]` 的时段里**，而且第 4 轮把 `[Shot 1]` 恢复成作者原文后**仍然跑偏** ——
说明不是某句话写坏了，而是机制问题。

## 三、根因：Ref2VA 的参考图不带时间位置

- `MiniMaxH3ReferenceToVideo.ref_images` 只是**条件**（进文本编码器 + 转 latent），**没有 `frame_idx`**；
  官方 ref2va 对非空参考图只做逐张编号（`<Picture N>`），不说它该出现在第几秒。
- H3 里唯一能指定「某画面出现在第几帧」的通道是 **`MiniMaxH3AddGuide` / `FallingTSH3AddGuide`** 的
  `minimax_keyframes`。

⇒ 在 ref2va 模式下，「某张参考图对应的内容出现在第几秒」**完全由散文决定**：散文里哪张参考图的
笔墨重、动作写得活，它就被提前用掉。这就是「把敲击写活 → 特写被提前」的因果。

**推论（本轮反复验证）：散文里的时间码是"建议"不是"约束"。** 顺序/时长要定死，只能上锚点。

副产物：`[Shot 1]` 一旦被手部笔墨占据，模型的「一次连续拉镜」也会被截断 —— 第 1 轮把 7 秒拉镜压成
2.5 秒就是这么来的。

## 四、硬锚点配方

### 4.1 接线（`FallingTSH3AddGuide`，官方 `MiniMaxH3AddGuide` 的 None 安全替代）

链式串在 `MiniMaxH3ReferenceToVideo.positive` 与 `BasicGuider.conditioning` 之间：

```
MiniMaxH3ReferenceToVideo.positive
  → G1.positive → G2.positive → … → Gn.positive → BasicGuider.conditioning
每个 Gn 另接：
  latent     ← MiniMaxH3ReferenceToVideo 的第 1 个输出（LATENT）
  vae        ← 视频 VAE 加载器            # 必需，见 §5-1
  image      ← FallingTSMarkDownTable 的对应 <Picture N> 输出槽
  frame_idx  ← PrimitiveInt（或 ComfyMathExpression 按秒换算）
  audio_vae / audio                      # 只在锚定音频时才接
```

- mdtable 输出槽约定：`0` = ID，`1..9` = `<Picture 1..9>`，其后是 `<Video 1..3>` / `<Audio 1..3>` / 提示词 / 宽 / 高 / 秒数。
- 空单元格输出 `None`，`FallingTSH3AddGuide` 会**原样透传 `positive`**（等价于该槽无锚点），所以同一工作流的其它行可以直接留空。

### 4.2 帧号

`frame_idx = round(秒 × 24)`（H3 固定 24fps）。15s 档 `length = 362` 帧。

| 意图 | 秒 | frame_idx |
|---|---|---|
| `[Shot 1]` 开场（雨窗特写） | 0.00 | 0 |
| `[Shot 1]` 拉镜落点（越肩宽景） | 5.50 | 132 |
| `[Shot 2]` 切入（手部特写） | 7.00 | 168 |
| `[Shot 2]` 结束（同图再钉一次） | 10.50 | 252 |

- **相邻锚点间隔 ≥ 1.5 秒**（官方 multiframe 红线）；上表 5.50→7.00 正好 1.5s，是边界值。
- **同一张图钉两次 = 定义区间**：只钉 7.00s 时，模型会在 9.4s 中途切回宽景 2 秒才切正面；
  再用 `<Picture 5>` 钉住 10.50s，特写就被锁在 7.0–10.5s，宽景插不回来。这是最有效的一招。
- 锚点帧号与提示词里的时间码必须**同步**维护（散文说 7.0s，锚点就得是 168）。

### 4.3 实测效果

| 方案 | 结构 |
|---|---|
| 改造前 | 雨窗+拉镜 0–3s → 越肩宽景 3–7.6s → 手部特写 7.6–11.2s → 正面 11.2–15s |
| 3 锚点（0 / 5.5 / 7.0s） | 雨窗→连续拉镜→宽景 0–5.9s → 特写 5.9–9.4s → **宽景 9.4–11.4s** → 正面 11.5–15s |
| **4 锚点（+ 同图 @10.5s）** | 雨窗→连续拉镜→宽景 0–6.9s → **特写 7.0–10.4s** → 约 1s 过渡 → 正面 11.5–15.04s |

4 锚点版把 `[Shot 1]` 的连续拉镜也一起恢复了（3 锚点版被压到 5.9 秒）。

### 4.5 ⚠️ 锚点接线是**按行接死**的：一条链只服务一行（2026-09-30 实测）

`FallingTSH3AddGuide.image` 直接接在 `FallingTSMarkDownTable` 的**固定输出槽**上，而「选第 N 行」只换

  **P5=手部修改特写** / P6=书房左前 —— §4.4 那张表就是按它接的（`0.00←槽3`、`5.50←槽4`、`7.00/10.50←槽5`）。

  **P4=手部修改特写** / P5=书房后左 / P6=书房左前。

**踩过的坑**：拿第 1 行的接线跑第 2 行，四路锚点全部接错图 —— `0.00s` 被钉上"手部修改全景"、`5.50s` 被钉上

## 五、坑（每条都真踩过）

1. **`vae` 是必需的**。核心 `MiniMaxH3AddGuide.execute` 在 `image` 有值而 `vae is None` 时抛
   `ValueError("anchoring guide frames needs the vae input")`。`audio_vae` 只在锚定音频时才需要
   （`anchoring guide audio needs the audio_vae input`），**不锚音频就别接**，少一路端口。
2. **否定式仍然不可靠**。第 2 轮写的 `carries no cut inside it` / `never moves in close on his hands`
   正是 `h3-scene-generation.md` 记过的陷阱（等于把不想要的运动/切法名字递给模型），本轮再次失效。
   一律正面陈述。
3. **布局第 2 条（端口上下顺序）对该节点有一条无法满足的例外**：`FallingTSH3AddGuide` 的前端端口顺序是
   `positive, latent, vae, audio_vae, image, audio, frame_idx` —— `image` 排在 `vae` 之后，而数据表节点在画布
   最上方（y=40）、VAE 加载器在 y≈1000+，因此「vae 上游在上、image 上游在下」做不到。
   **已发布的 `0043_关键帧视频.json` 同样如此**，属结构性强制的例外；其余各条（无重叠、上游右缘 ≤ 下游左缘、
   同列间距 50–100px）都要照常满足。
4. **帧号写死在 `PrimitiveInt` 里**：改提示词的时间码时必须同步改这些整数，否则散文与锚点互相矛盾。
5. **新增锚点节点后要按名字对齐控件、并逐条校验连线**：新节点 id / link id 必须递增写回
   `last_node_id` / `last_link_id`，且每条线的 `origin.outputs[slot].links` 与 `target.inputs[slot].link`
   都要成对登记。校验时**别拿具体类型去比通配 `*` 输出**：`FallingTSSwitch` 等路由节点的输出类型是 `*`，
   会把既有连线误报为"类型不符"。
6. **工作流 JSON 的 mdtable 快照不会因为 `--refresh-md` 而回写**。`workflow-to-prompt.py` / `run-workflow-by-name.py`
   的刷新只注入**本次 API 载荷**，磁盘文件仍留旧快照；要让文件与 md 一致，必须另外调
   `GET /fallingts_mdtable/read` 并写回 `widgets_values[0]` 与 `widgets_values_named.data`
   （两个镜像必须同步），否则下次在 F5 后打开会看到旧提示词。
7. **改工作流文件前先确认该工作流没开在浏览器里**：前端内存副本会在保存时整份写回磁盘，把脚本改的
   节点/连线覆盖掉。
8. **"机位静止窗"必须先逐帧剖面确认没夹进切点**。第六轮第一次测量取 5.60–6.95s 当静止窗，结果新片
   全幅中位 0.125→0.250、连"本应静止"的窗区都从 0.188 涨到 0.438，于是得出"手部相对运动反而下降"的
   **错误结论**；逐帧剖面一看才发现新片 **6.40–6.61s 已经在切镜**（旧片切在 6.76s），那个窗口把整幅
   切换瞬间算了进去。正确做法：先对 5.4–7.0s 逐帧打印「全幅 / 各 ROI」帧间差
   （`scripts/motion-frame-profile.py`，K 的规范名），找到两片都还没切、且全幅差已落到地板的区间，再取
   ROI 比较。
9. **H3 的切点有 ±0.3~0.5s 漂移，不能当硬约束**。同一行脚本写 `At 00:07.000 the shot cuts`，实测旧 take
   切在 **6.76s**、新 take 切在 **6.50s**；且新 take 的切入是 6.40–6.61 的**渐变糊**而非硬切。
   要精确切点只能靠锚点/后剪，不能靠散文里的时间码。
10. **跨 take 比较运动量一定要除以"同一 take 的静态控制区"**。H3 每次重roll 的雨量/颗粒都不同（本轮
   全局 +15%），绝对值会整体漂移；用画面里的静止结构（本例取右上角夜空，0.14–0.16 为地板）做分母，
   才能分辨"这块地方真的更动了"还是"整幅都更躁动了"。

## 六、什么仍然做不到

### 6.1 为什么"指尖敲击"在中景里做不出来：**一个 token = 32 像素**（根因，源码级）

H3 视频 VAE `space_down=(2,2,2,2,1,1)`（空间 16x）、`time_down=(1,2,2,1,1,1)`（时间 4x）
（`comfy\ldm\minimax\vae.py:407-437`），DiT 再按 `patch_size=(1,2,2)` 切一次（`minimax\model.py:476`）：

| 832x480 出片 | 值 |
|---|---|
| VAE latent | 52x30 |
| DiT token 网格 | 26x15 |
| **一个 token 覆盖** | **32x32 px** |
| 一个时间步覆盖 | **4 帧 = 1/6 s** |

越肩中景里 手+键盘 ≈160x100 px = **5x3 token**；单根手指 **< 1 token**；一次敲击指尖位移 2~4px =
**0.06~0.12 token** ⇒ 没有任何 token 的值会因这次敲击而改变，模型**在表示层面就没有位置**放这个动作，
提示词写得再狠也不会动。手部特写里手 ≈11x6 token，整个手的抬起落下（40~60px ≈ 1~2 token）才勉强可表示
—— 这也是特写里看到的是"手抬起/落下"而非逐指连打的原因（时间上 4 帧一步，每秒 7 次敲击 ≈ 0.86 步）。
→ 想让"灵活敲击"成立：**要么给特写景别，要么把动作换成 token 级容得下的大幅度动作**（见 6.2）。
**提高分辨率无效**（手占画面比例不变 ⇒ token 数不变）。

第五轮的反证（提示词已写"入画起就在敲、手指不停、音轨有键声"）：静止尾段手/键盘 ROI 只有 0.594，
同帧后背 0.219、窗 0.188 —— 手/背景 **2.7x**，与改造前（0.438/0.156 = **2.8x**）无差别。

### 6.2 提示词能把动作交给"手臂链"，但是量变不是质变（第六轮实测）

第六轮把 `[Shot 1]` 的动作口径从指尖细节改成**手臂链 + 上身起伏 + 短促不匀的爆发**（前臂绕肘转动、
肩随爆发前后滚动、上身随节奏轻晃、头随节奏小幅起伏，并写明"幅度清楚可读、不许僵住"），其余不动：

| 5.65–6.35s（两片都还没切镜） | 旧（指尖文案） | 新（手臂链文案） |
|---|---|---|
| 手/键盘 ROI 中位 | 0.681 | 0.851（**+25%**） |
| 手臂/后背区 ROI 中位 | 0.409 | 0.691（**+69%**） |
| **右上角静态控制区** | 0.156 | 0.140（**持平**） |
| 雨/窗区（全局参照） | 0.317 | 0.363（+15%） |
| **手臂区 ÷ 静态控制区** | **2.62x** | **4.94x** |

扣掉全局 +15% 后，手臂/上身确实多动了（≈+47%），手部只是边际改善（≈+9%）。肉眼：两轮 take 极像
（同种子），差异是"手在键面上下游走、右手抬起换位、前臂手腕跟着移动"这种**细微但可见**的变化，
不是"从不动到动"；没有乱挥/抽搐（自然度 OK）。→ 提示词路线**有效但幅度有限**，天花板由 6.1 决定：
**真正想看清动作，只有换景别（让手占更大画面比例）这一条确定路径。**
- **固定像素 ROI 会在拉镜/景别变化时量错对象**。本轮第一次测量把 ROI 放在 x180-360/y300-420,而那正是
  他的**后背**(`<Picture 4>` 里后背占左侧 40%,手在 x330-490),于是量到 0.25 的假阴性。
  正确顺序:先算**每像素时间中位数**的分布、用 top-0.5% 或 8x12 热区**定位运动在哪**,再据图选 ROI。
- **锚点只钉构图,不保证动作幅度**。手部是否灵动仍取决于散文怎么写（见
  `references/output-verification.md` 的运动量口径）。
- **1 秒左右的过渡段**：4 锚点版在特写与正面之间仍有约 1s 的「他坐桌前」画面，原版没有。
  要压掉它就得再给正面补一个锚点，而正面在这一行里没有对应的参考图可选。
