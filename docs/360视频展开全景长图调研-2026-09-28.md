# 360° 视频 → 球形四周展开长图 调研（2026-09-28）

**触发问题**：生成的世界模型重影严重，怀疑是「参考图 8 图有很多重复像素」；想找「从 360 度视频场景中获取球形四周影像展开为长图片」的功能。要求搜遍全网 + 本地所有工作流。

> ⚠️ 根 `scripts\` 临时目录已于 2026-10-11 移除，下文的 `scripts\_out-pano\*` 产物仅作历史记录。

---

## 0. 结论速览

1. **「8 图重复像素」不是重影的原因**（实测：相邻面 MAE≈24/255、去均值相关 corr≈0.09，是 8 张明显不同的画面；§1）。
   重影的机制是**每个视角各自预测相机位姿 + 各自预测单目深度**，上游推理又**不做跨视图融合**（`rasterization.py:240-242` 在 `is_inference` 直接 return），于是同一表面被两套「位姿/深度不一致」的反投影各铺一层壳。
2. **「球形四周展开为长图」= equirectangular / 圆柱投影，本来就是一个标准操作，不是新东西**：
   - 真 360 相机（Insta360 / Theta）导出的 mp4 **本身就是 equirect**——每一帧已经是那张长图，`ffmpeg` 抽一帧即可，**不需要任何"展开"步骤**；
   - 若是**双鱼眼**原始视频，用 `ffmpeg -vf v360=dfisheye:e` 转成 equirect（本机 ffmpeg 带 `v360` 滤镜，输入/输出共 24 种投影，§3.1）；
   - 若是**普通镜头原地旋转**拍出来的视频（本地的 `0031 旋镜视频` 就是），用「帧间位姿估计 + 圆柱反投影」拼长图 —— **本次已实测做通**（§4）。
3. **最关键的一条：本地 `ComfyUI-HYWM2` 已经装好了「长图 → 精确相机位姿 → 世界重建」的完整链路**，只缺「视频 → 一张长图」这一步：`HYWM2SamplePanorama`（Equirect → 视角切图，**同时输出 EXTRINSICS / INTRINSICS**）→ `HYWM2Reconstruct` 的 `prior_extrinsics` / `prior_intrinsics` / `prior_camera_json` 把精确位姿注入 WorldMirror 2.0（§2）。
   官方实测：**注入相机先验后重建误差从 0.033/0.037 降到 0.013/0.012（7-Scenes Point Map Acc），Re10K NVS PSNR 20.62 → 22.30**。

## 1. 先把前提钉死：8 张参考图**不是**重复像素

对 0034 实际喂进前馈的 8 张图（`ComfyUI\temp\worldrefine\8723b9869474bd13\00..07.png`，832×480）做量化（脚本 `custom_nodes\ComfyUI-FallingTS\dev\_check-0034-8views.py`）：

| 指标 | 相邻面实测 | 判读 |
|---|---|---|
| MAE（0~255） | 平均 **24.1**（≈9.4% 满量程） | 差异很大，不是同一张图 |
| 去均值相关 corr | 平均 **+0.094** | 基本不相关 |
| 缩略图最近邻重复率 | 平均 55.3% | **这个指标不可信**：同一房间本来就大量相似的墙/地板灰度，它量的是"室内场景的共性"，不是"图像重复" |

**结论**：8 张图是 8 个不同视角的真实画面；它们共享的只是"同一个房间"这件事——而共享内容恰恰是重建**需要**的重叠。重影来自**几何不一致**，不是来自"像素重复"。参照：ComfyUI-Sharp 官方文档对同类问题的原话是 *"predict depth independently for two photos of the same overlapping scene, and each prediction gets its own arbitrary scale. Nothing forces them to agree, because each view was estimated in a vacuum."*

## 2. 本地现成能力（零安装）

### 2.1 `HYWM2SamplePanorama` + `HYWM2Reconstruct`：长图 → 精确位姿 → 重建

已核实（读源码 + `/object_info` 确认已注册）：

- `custom_nodes\ComfyUI-HYWM2\nodes\sample_panorama.py`
  输入 equirect 全景 → 按 `fov_degrees=65` / `overlap_percent=10` / `output_size=952`（对齐 WorldMirror target_size，且下游按 ViT patch 14 对齐）切一网格视角，`skip_poles=True` 时竖向只覆盖 150°（±75°），默认 **7×3 = 21 个视角**。
  输出：`images` **+ `extrinsics`（w2c [N,4,4]）+ `intrinsics`（[3,3]）+ num_horizontal + num_vertical`。
  内参 `f_px=(output_size/2)/tan(fov/2)`、`cx=cy=(output_size-1)/2`；外参由 yaw(Y)+pitch(X) 旋转矩阵转置构成，**所有视角相机原点都在球心**（纯旋转）。
  文件头注明 *"Ported from ComfyUI-Sharp's SamplePanorama node"*。
- `custom_nodes\ComfyUI-HYWM2\nodes\reconstruct.py`
  输入 `prior_extrinsics` / `prior_intrinsics` / `prior_camera_json`（三选一或组合）→ `_dump_camera_priors_json()` 把 w2c **取逆成 c2w**、`camera_id` 填 PNG stem，写 `prior_camera.json` → 交上游 `pipeline._run_inference(prior_cam_path=...)` → `load_prior_camera()` → `WorldMirror.extract_priors()` 把相机、深度、内参变成 `cond_flags` 条件注入。
  分辨率策略已为这条路做了适配：注释原文 *"Auto-shrink further based on view count + free VRAM so a 21-view 952 panorama doesn't OOM on an 8 GB card"*（`_auto_target_size(len(img_paths), adaptive, free_gb)`）——**8 GB 的 4060 就是它设计里的目标机型**。
- 官方先验注入格式（HY-World 2.0 `DOCUMENTATION.md`）：`camera_params.json` = `{"num_cameras":N,"extrinsics":[{"camera_id":0,"matrix":4×4 c2w}],"intrinsics":[{"camera_id":0,"matrix":3×3}]}`；`camera_id` 可用图片文件名去扩展名；内参按原图分辨率给，pipeline 自动换算 resize+center-crop。

## 4. 实测：普通「原地旋转」视频 → 球形四周长图（本地 0031 旋镜视频）

**素材**：`media\七纹刻印\0031_首帧场景\00001_书房旋镜视频.mp4`（832×480 / 24fps / 243 帧 / 10.125s）。
**先核实它是不是真 360°**（`custom_nodes\ComfyUI-FallingTS\dev\_probe-0031-rotation.py`）：每 5 帧取一帧、ORB 匹配求水平位移——48 步位移全部一致（缓入缓出，-35~-55 px/步，匹配 200~1500 对），**首末帧 ORB 位移仅 +1.4 px（同一面墙）**，4×4 联络表肉眼确认：书桌/窗 → 书柜 → 门+挂钟 → 盆栽 → 回到书桌，**是完整的绕光心一圈**。

**方法**（`custom_nodes\ComfyUI-FallingTS\dev\_unfold-0031-360.py`，纯 CPU、无新依赖）：

1. 每帧取一帧（243 张），相邻帧 ORB 匹配求水平位移 `dx_i`（中位数 + 40px 离群剔除）；
2. **焦距 `f` 由闭环约束解出**：令 `Σ atan(|dx_i|/f) = 2π`（二分法）——因为纯旋转的转角是可加的，这条约束把"像素位移"和"角度"一次标定好；
3. 累加得每帧偏航 `yaw_i`；按圆柱投影重采样到一张长图：输出列 `θ` 用 `u = cx + f·tan(θ - yaw_i)`，竖向可分离；
4. **每列只用角距离最近的两帧做线性混合**（第一版用 ±60° 余弦窗口，等于把 27 帧平均，糊成一片；改最近两帧后变清晰 → 这是本次踩到的坑）。

**结果**：`f=337.8px → 水平 FOV≈101.8°`，长图 **2123×480（4.42:1）**，**未覆盖列 0**，首尾同为一扇门（闭环成立）。
产物：`scripts\_out-pano\surround-cylindrical.png` + 预览 `surround-cyl-243-preview.png`；另出 2:1 equirect `surround-equirect.png`（2123×1061，**有效覆盖仅 39%**：单目相机的竖直 FOV 只有 ~70°，上下极区必然缺）。

**质量与边界（诚实版）**：长图可读（门 / 书柜 / 盆栽 / 窗+书桌 / 挂钟 / 回到门），但仍有局部重影（挂钟出现拖影、书桌边缘模糊）。原因：① 1.48°/帧的位姿是"整帧中位数"估计，局部区域仍有 ±1~2px 残差；② H3 生成的视频本身帧间内容就在漂移；③ 圆柱竖向映射用的是线性近似。**要做成生产级，需要 per-column 局部对齐（或直接给每帧一个精确 yaw）**。它是**原理验证**，不是成品。

## 6. 明确做不到的

1. `ffmpeg v360` **不输出相机内外参**。
2. **`.insv` 等厂商专有格式读不了**，必须先经 Insta360 Studio 导出 equirect mp4。
3. **平移视频 → 干净长图**：无可靠开源方案。
4. 所有转换类节点/滤镜**都不做跨视图融合**；ComfyUI-Sharp `MergeGaussians` 官方原话：*"no ICP registration, no blending across overlapping regions, no deduplication of Gaussians that landed in the same spot from two different faces."* ⇒ **光有精确位姿不会自动消掉重叠区的重复高斯**。
5. 单目相机原地旋转得到的长图 **竖向覆盖有限**（本例仅 ±35°），2:1 equirect 的上下极区必然缺失；`HYWM2SamplePanorama` 默认 `skip_poles=True` 取 ±75°，直接喂会采到黑边，需要限制竖向 FOV 或补天补地。
6. `HYWM2SamplePanorama` 只处理 `panorama[0]`（单张），**视频批处理未验证**。
7. 全网**没有**"全景切图喂 3DGS 比独立 8 图重影更少"的公开对比实验（未验证，不要当事实引用）。

## 7. 推荐路线（按代价排序）

**路线 A｜真 360 素材（0 安装，最省事）**
360 相机/模型产出 equirect 视频 → `ffmpeg` 抽帧（或抽 N 帧取最清晰/最优曝光的一帧）→ `HYWM2SamplePanorama` → `HYWM2Reconstruct`（prior 自动接上）→ `WorldRefinePLY`。
代价：零安装，只改 0034 的连线。风险：单帧信息量有限；素材本身有接缝/视差就会带进重建。

**路线 B｜用现有旋镜视频自己展开（本次已做通，脚本在 `custom_nodes\ComfyUI-FallingTS\dev\_unfold-0031-360.py`）**
长图 → 裁成可用竖向范围 → `HYWM2SamplePanorama`（**必须把 fov/竖向范围调到不超过长图的有效带**）→ 重建。
代价：脚本已写好、幂等可重跑；**质量受帧间对齐精度限制**（要生产级需 per-column 局部对齐）。

**路线 C｜生成一张 equirect 再切（不依赖任何实拍）**
用本地就绪的 Qwen-Image-2512 + [qwen-360-diffusion](https://huggingface.co/ProGamerGov/qwen-360-diffusion) LoRA 生成 2:1 equirect（模板 `templates\图像\template_qwen_Image_2512_360_lora.json`，只缺 LoRA 权重），或直接用 RunningHub 那两个「图片转 360 全景图」工作流 → `HYWM2SamplePanorama` → 重建。
代价：要下一份 LoRA；好处：**一张图里几何天然自洽**（没有 8 张各自生成导致的位姿/内容不一致）。

**路线 D｜补融合与质检（中等）**
装 ComfyUI-Sharp，用官方 "Panorama gaussians" 工作流：`SamplePanorama` → `SharpPredictMetricDepth` → `AlignDepthMaps(global_optimization)` → 看 `disagreement_heatmap` 判断重叠是否够 → `ProjectDepthToPanorama` / `MergeGaussians`。这是唯一能对"重叠区不一致"做全局优化 + 可视化的现成方案。

**路线 E｜自写（最完备）**
`v360` 已解决投影，不必自己写。真正值得写的是：① 从相机标定/`rig_config.json` 反解精确外参；② 按已知位姿做**可见性剔除**（把相邻视角重叠区里"本视角不可见"的高斯先剔掉再合并）——`MergeGaussians` 明确不做这件事，而这正是"双层壳"的对症点。本地 `WorldRefinePLY` 的几何信任域精修已在做同类事，扩展它比新写节点划算。

## 8. 与 0034 现状的衔接

当前 0034：`md 表 8 视图 → WorldRefinePLY（504 前馈 + 2% 尺度过滤 + 3DGS 全参数精修，reg=3.0）→ PLY`。
8 张图是**模型/多视角 LoRA 分别生成**的，几何上互相不一致 → 上游按各自预测位姿反投影 = 2 层壳 = 重影（这正是 `reg` 要事后收拢的东西）。

**若改走路线 A/B/C**：把「8 张独立图」换成「**一张长图**（equirect）」，由 `HYWM2SamplePanorama` 供 21 个视角 + **精确位姿**，`HYWM2Reconstruct` 用 `prior_extrinsics/prior_intrinsics` 注入 —— 位姿不再由模型猜，壳从源头减少，`reg` 可以更小（保留更多细节）而不出重影。
