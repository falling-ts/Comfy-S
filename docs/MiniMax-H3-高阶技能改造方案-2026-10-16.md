# MiniMax H3 工作流高阶技能改造方案（2026-10-16）

把三类高阶技能落地到本机 **11 个 H3 工作流**：完美中文、画面/人物去油、远景小人物崩脸修复。
调研依据来自两条线：本机既有 4 篇专题文档（见文末「本机依据」）+ 一轮社区调研（见文末「社区依据」）。

## 0. 本机实况（先纠正一个过时前提）

| 项 | 实况 | 说明 |
|---|---|---|
| GPU | **RTX 4080 SUPER / 32760 MiB（32 GB）** | 不是 8GB。旧记录里的「8GB 显存硬瓶颈」在本机已不成立 |
| 内存 | **503 GB**（可用约 370 GB） | 足以支撑长视频 latent 二采与 tiled 解码 |
| ComfyUI | 运行于 `127.0.0.1:8188`，已注册 **2979** 个节点 | 改造前先核 `object_info` |

> ⚠️ **但 `MAX_PIXELS = 768 × 1344 = 1 032 192` 仍然是硬上限**，与显存无关。
> 它是 H3 的**训练分辨率上限**，超过会出克隆/复制伪影，不是 OOM 问题。
> 本方案所有二采目标尺寸都必须落在这条线以内。

## 1. 三类问题的根因（定调：全部是 token 问题）

H3 与 Qwen-Image 2.1 同口径：**1 token = 32×32 像素**。脸崩不崩，只取决于**脸占多少个 token**。

```
解码端脸高 token = frame_height × 脸占画面高度比 / 32
```

| 场景 | 480p（832×480） | 768p（1344×768） |
|---|---|---|
| 大特写（脸占 0.79） | 11.9 tok | 19.0 tok |
| 中近景 MCU（脸占 0.33） | 5.0 tok | 7.9 tok |
| 中景远景（脸占 0.15） | 2.3 tok | 3.6 tok |

**两条决定性结论**：

1. **`ComfyUI-H3-FaceRefine` 官方定性**：「H3 渲染人脸差，是因为**头占画面的比例小**。
   **这是 head-size-in-frame 的属性，不是输出分辨率的属性，所以 720p 以上依然存在。**」
   ⇒ 单纯升分辨率有天花板。
2. **`ReDetail`（LTX-2.5 精修）实测**：refine 模式「**无法修复源里已经崩坏的脸，它只是重建已经在
   那里的人脸的细节**」。
   ⇒ **崩脸必须在生成阶段解决，后处理救不回来。** 这条直接否决了「先出片再靠 LTX/ReActor 修」的路线。

## 2. 技能一：画面与人物去油（塑料感）

### 2.1 手段排序（按性价比）

| 顺序 | 手段 | 本机落地 |
|---|---|---|
| ① | **别盲目上 768p LoRA** | 768p 系本身自带「过饱和塑料感」（lightx2v discussions/27 多人实测）。本机 0013/0030/0033/0040-0042 都挂 `fl2v_turbo_4step_v1.0_768p` + shift 6/3 —— 这是**已知更油的一档** |
| ② | **专用真实感 LoRA** | `h3-realism-people-t2v-i2v-r2v`，**触发词 `r34l1sm`**，官方推荐 1.0、本机主流 0.75–0.9 |
| ③ | **质感受 LoRA** | `Minimax-H3真实电影质感V0.1-解决张量报错` @0.2–0.5（本机 17 个工作流在用，主力 0.2/0.5） |
| ④ | **二采低 denoise** | 本机共识 **0.35**；配 `beta`/`simple` + `euler` |
| ⑤ | 后处理 | `ltx-2.5-22b-ic-lora-restore-1.0` / `ltx-2-19b-ic-lora-detailer` |

### 2.2 落地接线

去油 LoRA 插在 **LoRA turbo 之前、`MiniMaxLowVRAMAttention` 之后**（共享给 4 步与 8 步两条链）：

```
SageAttentionPatch → [去油LoRA: realism @0.8] → [质感LoRA: 电影质感 @0.3] → LowVRAMAttention
                                                                                    ├→ LoraLoaderModelOnly(turbo 4step) → SigmaShift → ...
                                                                                    └→ LoraLoaderModelOnly(turbo 8step) → SigmaShift → ...
```

**可切换**：用 `FallingTSSwitch`（`total=1`）做 MODEL 二选一 —— `false_1` = 原始 chain，`true_1` = 经去油 LoRA；
一个节点同时管住两条链，关掉即完全等于改造前行为。

**触发词**：`r34l1sm` 必须出现在提示词**最前面**。用 `StringConcatenate` 注入，不修改 md 数据表：
`PrimitiveString("r34l1sm, ")` + `md表输出` → `StringConcatenate` → `CLIPTextEncode.text`。

> ⚠️ **`r34l1sm` 只在启用去油 LoRA 时才该存在**。若 `FallingTSSwitch` 关掉 LoRA 而触发词还在，
> 触发词会变成一个无意义的 prompt token。两者由同一个 `switch` 布尔驱动即可（LoRA 走 switch，
> 触发词走 switch 的 BOOLEAN 输出）。

### 2.3 明确不要做的事

- **不要**用 `skin-LTXLora-step00004000`：那是 **LTX 侧** LoRA，喂给 H3 无效。
- **不要**用 `Detailer-KREA2`：本机 5 个 Krea2 图像工作流在用，**无一用于 H3**。
- **不要**叠超过 3 个风格 LoRA：本机实测与社区共识都是「LoRA 过多互相打架、拖慢速度」。

## 3. 技能二：完美中文

### 3.1 铁律：格式契约必须原样英文，中文只允许出现在两处

官方 `ref-en.txt` L5 原文：

> `Write all six rewrite sections in English. Preserve the original language only for dialogue and lyrics inside <d> and for text visibly present in the scene.`

⇒ 六段结构段名、`<Subject N>` / `<Picture N>` / `<Video N>` / `<Audio N>`、`[Shot N]`、
时间戳 `00:08.000`、`retention_analysis` 枚举值 —— **一律英文，不能中文化**。
**中文只允许出现在**：① `<d>…</d>` 内；② 画面中**实际可见**的文字。

### 3.2 中文台词的唯一正确写法

```
(S1) <d>[Chinese] 你刚才说的那句话，再说一遍。</d>
```

- `<d>` / `</d>` 是**词表外 special token**（id 151669–151675），由 ComfyUI 加载时注入。
  写成 `<对话>` 之类**静默失效**，不报错。
- **不需要拼音**：官方无任何音标/拼音输入接口。
- 不可辨识片段写 `[unclear]`（ref-en.txt L274），**不要猜译**。

### 3.3 中文的已知代价（本机受控实测，必须接受）

| 项 | 英文 | 中文 |
|---|---|---|
| 估计人脸年龄 | 25.2–26.1 | **27.1–29.4**（+2~3 岁，两组**零重叠**） |
| ArcFace 余弦相似度 | 0.518–0.713 | 0.556–0.677（**重叠** ⇒「中文换了个人」是谣言） |
| 镜头/时间轴/音轨/手部 | 无可见差异 | 无可见差异 |
| 音频 LUFS | 差 <1 dB | 差 <1 dB |

- **年龄感 +2~3 岁用「严格要求」的措辞补不回来**（已实测）。
- 景别漂移：中文更易拍成大特写（脸高 0.79 vs 0.35）。
- **否定句会反噬**：写「不要大特写」反而更容易大特写。

⇒ **推荐写法「骨架英文，血肉随意」**：
`<Subject N>` 身份段 + 景别段用**英文**，其余叙事散文可用中文。

### 3.4 口型错人：最普遍的失败模式，且有解

一手实测（`zenstory-ai/drama-skills` PR #169）：远处小孩喊话、近处骑手正面出镜时，
**3 次中 2 次口型落在骑手身上、小孩闭嘴**。根因是「**模型把口型给了画面里最显眼的正脸**」，
不是声音选错（19 条样本发声基频都在儿童区间）。

**有效对策（按优先级）**：

1. **让不说话的人出画或背身** —— 骑手出画后 12 次全部正确。分镜能安排时这是最优解。
2. **明写不说话的人闭嘴**：`The messenger does not speak; his lips remain completely closed.`
   加写后 3 次全部正确。
3. **画外音不要用 `the man` 指代 narrator**（会被当成画面里那个人而驱动其嘴）。
   改用 `Female narrator voice, saying: "…"`。

⚠️ HuggingFace `Comfy-Org/MiniMax-H3/discussions/44` 记录：8 种「旁白/画外音」写法**全部无效**，
只有上面第 3 条有效。内心独白「时灵时不灵」。

### 3.5 画面中文文字：不要指望 H3 生成

waveSpeed 与社区工程结论一致：**视频模型生成的可读文字普遍糊/错字/逐帧抖动**，
「一个拼错的产品名留在画面里，比没有文字更糟，而且事后无法可靠修复」。

**落地做法**：

- **画内少量文字**（招牌、书页、手机屏）：写进提示词没问题（官方允许保留原文语言），
  但**只作风格要素，不作信息载体**。
- **字幕 / 标题 / 台词**：走后处理叠加。本机已有渲染链：
  - `FallingTSImageComposite`（随包 CJK 字体 `fonts/Alibaba-PuHuiTi-Heavy.ttf`，`draw.text(stroke_width)`）
  - `DrawText+`（`ComfyUI_essentials`，支持 `font` / `size` / `color` / 对齐 / 描边阴影）
- **字幕与画内文字必须分开写**（drama-skills PR #88）：字幕**不要**写进生成提示词。

### 3.6 口型矫正的正统解法（若需要驱动既有音频）

H3 是**原生音视频联合模型**，生态正解**不是** LatentSync / Wav2Lip，而是**把真实音频锁进 AV latent**：

- 节点 `MiniMaxH3NativeAudioLock`（来自 `Shrek3OnVH5/MiniMax-H3-NativeAudio-MusicVideo-Workflow`）：
  把音频编码进 AV latent 的音频流，设 `noise_mask` **视频=1 / 音频=0** ⇒ 只有视频去噪，
  视频分支 cross-attend 到固定音频上 —— **这就是塑造嘴型的机制**。
- 喂**分离出来的 vocals 轨**信号更干净；原始音频另走一路进保存节点。

⚠️ **本机未安装**该节点包（见 §6「需额外下载」）。当前 11 个工作流靠**提示词侧**控制口型。

## 4. 技能三：远景小人物崩脸修复（H3 latent 二采提 token）

### 4.1 为什么选 latent 二采

对比三条路线：

| 路线 | 提 token 效果 | 成本 | 本机依赖 |
|---|---|---|---|
| **H3 latent 二采**（本方案） | 脸 token **×2.6~4** | +80% | ✅ **全部已有** |
| 逐帧裁脸重绘贴回（FaceRefine） | 最高（脸填满 768×768 画布） | +200% | ❌ 需装节点包 |
| 后处理修脸（ReActor/CodeFormer） | 不增加 token，只是替换 | 低 | ✅ 已有 |

**关键机理**：`MiniMaxH3LatentUpscale` 在**潜空间**把 24 通道 video latent 的 H×W 放大，
于是二采在**更高 token 密度**的网格上重采样 —— 脸在采样时就占了更多 token，
细节因此被真正重建出来（而不是被插值放大）。

这也正好绕过了 §1 那条死路：**H3 latent 二采是在生成阶段提高 token 密度**，不是事后放大像素。

### 4.2 尺寸核算（这是本方案最硬的一步）

`MiniMaxH3LatentUpscale` 只接受 `scale_by`（倍数），**没有 target-dimensions 模式**。
而 H3 的上限是 `MAX_PIXELS = 1 032 192`（1344×768）。所以倍数必须**随一采档位变化**：

| 一采档位 | 像素 | latent(H×W) | **scale** | 二采 latent | **二采像素** | 合规 |
|---|---|---|---|---|---|---|
| 横480 | 832×480 | 30×52 | **1.6** | 48×84 | **1344×768** | ✅ = MAX_PIXELS |
| 竖480 | 480×832 | 52×30 | **1.6** | 84×48 | **768×1344** | ✅ |
| 横544 | 960×544 | 34×60 | **1.4** | 48×84 | **1344×768** | ✅ |
| 竖544 | 544×960 | 60×34 | **1.4** | 84×48 | **768×1344** | ✅ |
| 横768 | 1344×768 | 48×84 | **1.0** | 48×84 | 1344×768 | ✅（已在最高档，不提 token） |
| 竖768 | 768×1344 | 84×48 | **1.0** | 84×48 | 768×1344 | ✅ |
| 横/竖1088 | 同 544 | — | **1.4** | — | — | ✅ |
| 默认 | 随 md 表 | — | **1.4** | — | — | 保守值 |

- `snap_up` 向上取整到 **2 的倍数**（DiT patch `(1,2,2)` 硬约束）：
  `832×480 → latent 52×30 → ×1.6 = 83.2×48 → snap 84×48 → 1344×768` ✅
- **1.4 与 1.6 两个值都精确落在 1344×768**，这不是巧合 —— 是 H3 原生分辨率的吸引力。

**落地点**：尺寸档位 `FallingTSSelector` 的 `total` 从 **2 扩到 3**，
新增一组 `scale_by`（组内按同一批档位名给出倍数）。前端增删只动尾部 ⇒ **已有连线槽位不漂移**。

### 4.3 完整接线（照官方 `example_workflows/minimax_h3_*_two_pass_upscale.json`）

```
一采 SamplerCustomAdvanced ──► LTXVSeparateAVLatent ──┬─ video_latent ─► MiniMaxH3LatentUpscale(scale_by)
                                                      └─ audio_latent ─────────────────┐
                                                                                        │
   MiniMaxH3ConditioningUpscale(同一 scale_by) ◄── 一采 conditioning (positive)          │
            │                                                                           │
            ├──► BasicGuider(二采)                                                        │
            │                                                                           │
   ManualSigmas(二采) ──┬──► MiniMaxH3AddNoise(video) ◄── MiniMaxH3LatentUpscale         │
                        │            │                                                  │
                        └──► MiniMaxH3ShiftSigmas(video→audio) ──► MiniMaxH3AddNoise(audio) ◄── audio_latent
                                                  │                   │
                                     LTXVConcatAVLatent ◄──────────────┘
                                                  │
   RandomNoise ──► SamplerCustomAdvanced(二采, DisableNoise) ──► VAEDecode / VAEDecodeAudio
```

**三个源码级坑（必须遵守，否则静默坏掉）**：

1. **必须用 `MiniMaxH3AddNoise`，不能用原生 `AddNoise`**。
   H3 是 CONST 参数化的 flow 模型，标准 `AddNoise` 的输出会在二采采样器内部再被
   `(1-sigma)` 缩放一次 ⇒ **输出近纯噪声**。`MiniMaxH3AddNoise` 先做 `inverse_noise_scaling` 抵消。
2. **音频支路必须走 `MiniMaxH3ShiftSigmas`**。
   DiT 内部音频跑自己的 shift（3.0），而采样器的 sigmas 在视频 shift 上（6.0 或 12.0）。
   用原始视频 sigma 给音频加噪 = 音频失真。**`shift_video`/`shift_audio` 必须与一采的
   `MiniMaxH3SigmaShift` 一致**（见下方档位表）。
3. **`MiniMaxH3ConditioningUpscale` 的 `scale_by` 必须与 `MiniMaxH3LatentUpscale` 完全相同**。
   两者不同 ⇒ `minimax_refs` / `minimax_keyframes` 的 token 尺度与 RoPE 行布局错位，**不报错但画面错**。

**shift 配对（铁律，从工作流现读，不硬编码）**：

| 工作流 | 一采 LoRA | shift(video/audio) |
|---|---|---|
| 0013 / 0030 / 0033 / 0040 / 0041 / 0042 | `fl2v_turbo_4step_v1.0_768p` | **6 / 3** |
| 0031 | `fl2v_lightx2v_turbo_4step_v0.1`（544p 档） | **12 / 3** |
| 0014 / 0032 / 0043 / 0044 | `ref2v_turbo_*` | **12 / 3** |

> 二采的 `MiniMaxH3ShiftSigmas` 用**与一采相同的 shift** —— 因为二采复用同一个 MODEL
> （同一个 LoRA、同一套 `MiniMaxH3SigmaShift`）。脚本从工作流现有节点的 `widgets_values` 现读。

### 4.4 二采强度

本机共识 **denoise 0.35**（`MiniMaxH3TwoPassDetailMixer` 14 个工作流一致），
社区「双采样/双时钟」同现去油。二采 `ManualSigmas` 取 **4 步、起点 0.55**（中等强度）：

```
0.55, 0.40, 0.22, 0.0
```

- 太低（<0.3）⇒ 细节补不出来，白跑一遍。
- 太高（>0.8）⇒ 重画内容、可能改变表情与身份。
- 4 步与一采的 turbo 档一致，二采成本约为一采的 1/2（token 多了但步数相同）。

### 4.5 与既有 LTX-2.5 二采的关系（0040–0044）

0040–0044 已接 **LTX-2.5 二采**（latent 2× → 1088p，做高清化）。两者**不冲突，分工明确**：

```
H3 一采(480p/544p)  ──►  H3 latent 二采(→768p, 治崩脸/提 token)  ──►  LTX-2.5 二采(→1088p, 高清化)
```

- H3 二采**在 H3 模型内**进行，输出仍是 H3 原生的 AV latent ⇒ **音画同步不受影响**。
- LTX 二采读的是 H3 解码后的帧批，尺寸自动跟随（`GetImageSize` 直连），**无需改动**。
- 顺序不能颠倒：LTX refine **无法修复已崩坏的脸**（§1），必须在 H3 阶段先解决。

### 8.2 构建脚本

`custom_nodes/ComfyUI-FallingTS/dev/build-h3-advanced-workflows.py`

- **幂等靠「从备份基线重建」，不是靠 strip 增量**。技能一是把 Sage 原有的 MODEL 消费者
  **原地改接**到开关 —— 这条连线从 `links` 表里消失后，按标题前缀 strip 掉新增节点
  **恢复不了它**。所以脚本每次从 `backups/backup-<名>-20261016-H3高阶技能改造前.json`
  读入、重新拼装、覆盖 `workflows/`；基线缺失直接报错退出，绝不静默就地改造。
  （实测：连跑两次 11 个文件 sha256 逐字节一致。）
- 沿用 `build-ltx-upscale-workflows.py` 的范式：`next_id` 不掺 `last_node_id`、
  `relink` 重建双向连线、反向拓扑深度布局。
- 新增节点整块摆在**所有原有节点右侧 + 200px**（动态计算，不写死 12000 —— 0040–0044
  已有 LTX 二采链占据右侧，写死会成片重叠）。

### 8.3 已通过的校验

- 节点 id / link id 唯一；连线三处（`links` 表、`inputs[].link`、`outputs[].links`）双向一致；
  无悬空端口；无重复落到同一端口。
- 所有节点类型均已注册（2979 个）。
- 所有必填输入要么已接线、要么由 widget 供值。
- 新增节点与原有节点**零重叠**，横向间距 200px。
- 二采目标尺寸全部 ≤ `MAX_PIXELS`(1 032 192)：480p×1.6 / 544p×1.4 / 768p×1.0 → 均落在 1344×768。
- **重跑幂等**：连跑两次 11 个文件逐字节一致。

### 8.4 三个实现级坑（改脚本前必读）

1. **`FallingTSSelector` 的输入端口前面还有 `items`/`total`/`selection` 三个 widget 端口** ——
   追加新组时索引要用 `len(inputs)`，不能用「inputN 的个数」。用错会把新连线接到第 2 组
   末尾那几个已有端口上，原有连线被静默挤掉。
2. **`find_size_selector` 不能只认「widgets[0] 以 `默认,` 开头」** —— 步数选择器的 items 是
   `默认,8步,4步`，同样以「默认,」开头。可靠判据是「第一组端口数 == 9」。
3. **`FallingTSSwitch` 的端口名必须是英文原名 `false_1`/`true_1`** —— 引擎按 name 传 kwargs，
   写中文会永远取到 None 且不报错。

### 8.5 使用与回退

- **前端必须重新加载**：改工作流前先关掉对应标签页，改完再打开（F5 强刷），
  否则前端内存副本会把改动整份写回覆盖。
- **逐项旁路**：把「H3高阶 · 去油开关」的 `switch` 设为 `false` 即回到未去油；
  把「H3高阶 · 二采 · 预览/保存」节点 `mode` 设为 `4`（bypass）即只跑一采；
  删掉 `H3高阶 · 触发词 r34l1sm` 恒定值即撤掉触发词。
- **整体回退**：从 `backups/` 里的基线文件覆盖回 `workflows/`。
- **改前备份**：`backups/backup-<工作流名>-20261016-H3高阶技能改造前.json`（11 份）。
